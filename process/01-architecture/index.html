Process · 01 · Architecture

The shape

Two screens, one panel, one weekly job. A small stack designed to disappear under the content.

I — Map of the app

Two screens, one panel

The whole surface area is a list of doors, a room behind each door, and a side drawer that holds long memory. Everything else is a job that runs lazily in the background of a request.

The deliberate shallowness matters. Atrium has no settings page, no profile screen, no archive view, no analytics tab. There is no place to get lost. If you can’t reach the thing you want in one tap from the atrium, it probably shouldn’t exist in v1.

surface area of Atrium, v1

Component inventory

  • Atrium (home). A single vertical list of twelve doors. Each row: Latin name, italic definition, open-todo count.
  • House view. Header strip (back link, name, definition, gear). Two panes on desktop, two tabs on mobile.
  • List pane. Open todos sorted by priority, divider, recently-completed (faded), shelved disclosure.
  • Chat pane. Week-scoped conversation. Summary card pinned at top after a rollover. Inline propose_todo cards live within message bubbles.
  • meta_md panel. Slide-out drawer from the right. Markdown editor for long-lived per-house context.
  • Weekly rollover job. Not a screen. A function that runs on first house-open after Sunday 23:59. Locks the prior week, generates a summary, opens a new week.
Surface area discipline
Two screens and one drawer is a constraint, not a starting point. Any new screen proposed in the future has to justify itself against the cost of breaking the “list of doors, room behind each door” metaphor.
II — Core user journeys

What people actually do

Six flows cover the entire app. If a feature isn’t in service of one of these, it’s out of scope.

A
The daily entrance
Open the app. See the twelve names. Choose where to spend yourself today.
  1. Open Atrium. GET /
  2. Read the twelve doors. The open-todo counts give peripheral hint, no more.
  3. Tap a row. GET /h/[house_id]
  4. Land in the house. Pick up where the conversation left off, or attend the list.
This is the most-trafficked path in the app. It must feel like opening a door, not loading a dashboard. Cold-load budget on the home screen: under 200ms perceived.
B
Tending the list
Manual capture and care of todos — the bread-and-butter loop.
  1. Inside a house, type at the top of the list. ＋ add…
  2. Press enter. Todo created with source: 'manual'. Appears at top of open list.
  3. Drag to reorder, updating priority.
  4. Long-press any item for the menu: done · shelve · unshelve · delete.
  5. Completed items fade and strike through; persist for 7 days under a divider.
  6. Uncompleting returns the todo to the bottom of the open list.
Shelve is the default soft-delete. Delete requires a confirmation modal. Atrium remembers; it does not erase by accident.
C
The thinking-partner conversation
Talk through what’s in this house. Let action-shaped items surface deliberately, never silently.
  1. Type into the chat pane. POST /api/chat
  2. Server constructs the prompt: house definition + open todos + meta_md + last week’s summary + role instruction.
  3. Stream the response into the pane. Tokens flow as the model writes.
  4. If the model identifies an action-shaped item, it calls propose_todo. The tool call renders as an inline card: Add / Edit / Skip.
  5. User confirms. New todo created with source: 'chat' and chat_message_id set to the message that proposed it. POST /api/todo
  6. The chat-origin marker on the todo can later scroll the conversation back to the proposing message.
No background extraction. The user always sees the proposal before it enters the list. The Skip action records the proposal as skipped, useful later for tuning the prompt.
D
Editing the long memory
Update what the partner knows about this house — the names, the projects, what enough means.
  1. Tap the gear in the house header.
  2. A panel slides in from the right with a markdown editor for meta_md.
  3. Edit freely. Save on close (or autosave on debounce).
  4. Next chat turn includes the updated meta_md in the system prompt.
This is the field that makes the partner genuinely useful over months. It carries names, projects, hard-won shorthand — the things the user shouldn’t have to re-explain every Monday.
E
The Sunday rollover
Weeks end at 23:59 Sunday local. Nothing fires at midnight. The rollover happens lazily, on next entry.
  1. User opens a house after Sunday 23:59. GET /h/[house_id]
  2. Server checks: is there an active week whose end_date has passed?
  3. If yes, mark the week closed. Lock its messages.
  4. Generate the summary in one LLM call: transcript + end-of-week list state → 200–400 word markdown. opus-4-7
  5. Save summary_md on the closed week. Mark summarized.
  6. Create a new Week with the summary card pinned at the top.
  7. If the closed week had zero messages, skip steps 4–5. New week begins blank.
Houses untouched for a full week generate no Week row at all. The data model stays sparse. Cost stays sane.
F
Following a chat-born todo back to its origin
Months later, you wonder why this todo is here. Atrium can answer.
  1. Tap the small chat-origin marker on a todo.
  2. Conversation pane scrolls to chat_message_id, highlights the surrounding turn.
  3. If the message was in a prior week, Atrium opens that week’s locked thread.
A small affordance that pays for itself the first time you use it. Provenance is cheap to record and expensive to reconstruct after the fact.
III — Technical infrastructure

A small stack, picked for longevity

Atrium is a single-user tool. The stack should be boring, cheap to host indefinitely, and easy to leave alone for months between changes.

The layers, picked

Client
Next.js · App Router
react 18 · server components · tailwind or vanilla CSS · vercel ai sdk for streaming · EB Garamond via next/font
A single deployment unit (UI + API) keeps the operational surface small. Server components let the home screen render in one round-trip with seeded data. SvelteKit would be equally fine; Next.js wins on AI SDK ergonomics.
Data
Drizzle ORM over SQLite
drizzle-orm · libsql/turso for hosted · or better-sqlite3 for local file · migrations in /drizzle · seed script for the twelve houses
SQLite is the right size for one user with a few hundred todos and a couple of years of conversation. Turso (libSQL) gives you the same engine reachable from phone and laptop, with edge replicas, for a few dollars a month. Local-only mode is one env flag away if you ever want to leave hosting behind.
LLM
Anthropic API · direct
@anthropic-ai/sdk · claude-sonnet-4-6 default · claude-opus-4-7 for summary · tool use for propose_todo · prompt caching on the static system block
No middleware (no LangChain). Direct SDK calls are simpler to reason about and cheaper to debug. The system prompt for each house is largely static within a week — prompt caching reclaims most of the per-turn token cost.
Auth
Single shared secret
middleware checks ATRIUM_SECRET cookie · one-time set via magic link or env-var bootstrap
v1 is single-user. A full auth stack is an order of magnitude more code than the app deserves. If a second user ever needs in, swap to Clerk or Lucia in a day.
Deploy
Vercel + Turso
git push to deploy · environment vars: ANTHROPIC_API_KEY, TURSO_URL, TURSO_TOKEN, ATRIUM_SECRET · preview deploys per branch
Standard Vercel deploy + a Turso database. Total infra cost target: under $5/month before LLM usage. The contemplative tool should not have an operational footprint that demands attention.

The LLM contract

Every chat turn assembles the same prompt structure server-side:

┌─ system ──────────────────────────────────────────┐
│  role instruction (static)                       │
│    "You are a thinking partner inside the         │
│     house of [name]…"                             │
│                                                   │
│  house definition (verbatim, per-house static)   │
│                                                   │
│  meta_md (per-house, slow-changing)              │
│                                                   │
│  last week's summary (per-week, static once set)  │
│                                                   │
│  current open todos (volatile)                   │
└───────────────────────────────────────────────────┘
┌─ messages ────────────────────────────────────────┐
│  full week-scoped transcript                      │
└───────────────────────────────────────────────────┘
┌─ tools ───────────────────────────────────────────┐
│  propose_todo(text: string)                       │
│    → renders as inline confirmation card          │
└───────────────────────────────────────────────────┘

prompt cache the first four blocks; only the last two change per turn

The first four system blocks change rarely. Anthropic prompt caching on the static prefix reduces per-turn cost to roughly the volatile-todos block plus the conversation tail. For a house with steady use, that drops chat to a few cents per day.

Cost

Twelve houses, ongoing conversations, weekly summaries, real use — non-trivial token spend, but bounded. Rough envelope:

  • Chat turn (Sonnet, cached prefix): ~$0.005–$0.02 per turn.
  • Weekly summary (Opus, one call per active house): ~$0.10–$0.30 each. 12 houses × 4 weeks ≈ $5–$15/mo if every house is active.
  • Realistic monthly total at heavy use: $20–$50.

Settings shows a running monthly token counter with a soft cap. First month calibrates expectations — until then the cap is advisory.

Operational principle
Atrium should be the kind of tool that runs unattended for months. No cron jobs to monitor, no queues to drain, no schemas to migrate on a deadline. The only required scheduled work — weekly rollover — runs lazily inside a normal request. There is no separate worker process.

Two screens. One drawer. One lazy weekly job.
Everything else is just the rooms breathing.
