Process · 03 · Construction

On building

iOS first. SwiftUI on top, SwiftData beneath, an Anthropic stream feeding each room. And a long look at the part still under-designed — how the houses remember.

I — Pivot

Native iOS, then maybe the web

Change from Process 01
Atrium is now a native iOS application first. A web client is deferred until there is an actual second surface to serve.
The contemplative register asks for a tool that lives in the same pocket as the body. The home screen wants to be the first thing the thumb finds, not a tab in a browser. Notifications — even if v1 has none — will eventually want the system surface. The conversation pane wants voice; voice on iOS is one capability away, on web it is an arms race. SwiftUI’s typography honors a serif more gracefully than most browsers do.

What survives the pivot

Almost everything that mattered. The brief is platform-agnostic; the architecture page’s domain choices (twelve houses, weekly rollover, propose_todo tool, meta_md) carry over unchanged. The Anthropic API stays direct — called from the device. The data model is the same shape. The aesthetic stays.

Privacy as a quiet consequence
Going iOS-first with on-device SwiftData + CloudKit private database + user-supplied Anthropic key means no third party (including us) ever sees a token of conversation. Atrium becomes a tool whose privacy story is structural, not promised. This is the deeper reason for the pivot.

The atrium screen, in 30 lines of SwiftUI

/Atrium/Screens/AtriumView.swift
import SwiftUI
import SwiftData

struct AtriumView: View {
    @Query(sort: \House.order) var houses: [House]

    var body: some View {
        NavigationStack {
            List(houses) { house in
                NavigationLink(value: house.id) {
                    HouseDoor(house: house)
                }
                .listRowBackground(Color.paper)
                .listRowSeparatorTint(.rule)
            }
            .listStyle(.plain)
            .navigationDestination(for: String.self) { id in
                HouseView(houseID: id)
            }
            .background(Color.paper.ignoresSafeArea())
        }
    }
}

struct HouseDoor: View {
    let house: House
    @Query private var openTodos: [Todo]

    init(house: House) {
        self.house = house
        let id = house.id
        _openTodos = Query(filter: #Predicate<Todo> {
            $0.house?.id == id && $0.status == .open
        })
    }

    var body: some View {
        HStack(alignment: .firstTextBaseline) {
            VStack(alignment: .leading, spacing: 2) {
                Text(house.name).font(.garamond(.title2))
                Text(house.definition)
                    .font(.garamond(.body).italic())
                    .foregroundStyle(.inkSoft)
            }
            Spacer()
            Text(openTodos.isEmpty ? "—" : "\(openTodos.count)")
                .font(.mono(.caption))
                .foregroundStyle(.inkFaint)
        }
        .padding(.vertical, 6)
    }
}
III — How components talk

Four patterns, no more

SwiftUI begs for too many state-passing mechanisms. We commit to four, deliberately. Anything that doesn’t fit becomes a smell to investigate, not an excuse to add a fifth.

A — Read
@Query from SwiftData
Anything persistent flows from SwiftData. Views declare what they want; the framework keeps them in sync with the store. No fetching, no caching, no manual invalidation.
@Query(filter: #Predicate<Todo> {
    $0.house?.id == houseID && $0.status == .open
}, sort: \.priority)
var openTodos: [Todo]
B — Write
@Environment(\.modelContext) for mutations
Inserts, updates, and deletes go through the context. Views that mutate hold a context handle and call .insert, .delete, or just touch a property. SwiftData persists on the next runloop tick.
@Environment(\.modelContext) private var ctx

func addTodo(_ text: String) {
    let todo = Todo(text: text,
                    house: house,
                    status: .open,
                    priority: nextPriority(),
                    source: .manual)
    ctx.insert(todo)
}
C — Coordinate
@Environment for shared coordinators
Cross-cutting services — LLMClient, RolloverCoordinator, ProposalStore — are @Observable singletons injected at the root and read by any view that needs them. Not singletons in the global-state sense; just one instance, scoped to the app.
// AtriumApp.swift
var body: some Scene {
    WindowGroup {
        AppRoot()
            .environment(LLMClient.shared)
            .environment(RolloverCoordinator())
            .environment(ProposalStore())
    }
    .modelContainer(for: [House.self, Todo.self,
                              Week.self, Message.self,
                              TodoProposal.self])
}

// ChatPane.swift
@Environment(LLMClient.self) private var llm
@Environment(ProposalStore.self) private var proposals
D — Stream
AsyncStream<ChatEvent> for the chat
The streaming chat is the one piece of state that doesn’t belong in SwiftData mid-flight. The pane subscribes to an async sequence of ChatEvent values and updates @State as deltas arrive. When the turn closes, the assembled message is persisted.
// LLMClient.swift
enum ChatEvent {
    case textDelta(String)
    case toolCall(ToolCall)            // → ProposalStore.register(...)
    case turnEnded(assembled: String)
}

extension LLMClient {
    func stream(_ input: ChatInput) -> AsyncStream<ChatEvent> {
        AsyncStream { continuation in
            Task {
                for try await chunk in try await sse(input) {
                    continuation.yield(parse(chunk))
                }
                continuation.finish()
            }
        }
    }
}

// ChatPane.swift
.task(id: pendingPrompt) {
    guard let input = pendingPrompt else { return }
    for await event in llm.stream(input) {
        switch event {
        case .textDelta(let s): streaming += s
        case .toolCall(let t): proposals.register(t)
        case .turnEnded(let full): persist(full)
        }
    }
}

No third state
Nothing lives in some-other-store-besides-SwiftData. The streaming buffer is @State; everything else is SwiftData. This is what makes CloudKit sync “just work” later — there is no parallel cache to reconcile.
IV — Memory

The chat, the context, and what they remember

The original brief specifies four moving parts to memory: meta_md, the in-progress weekly conversation, the previous week’s summary, and the open-todo list. These are concatenated into the system prompt each turn. It is a reasonable starting point. It is also the part of the design most likely to need a second pass.

What is currently in the prompt

┌─ system ─────────────────────────────────────────────────┐
│  role instruction          — static, per-house          │
│  house.definition          — verbatim, per-house static │
│  house.metaMd              — user-edited, slow          │
│  lastWeek.summaryMd        — set once per rollover      │
│  openTodos                 — volatile, current state    │
└──────────────────────────────────────────────────────────┘
┌─ messages ──────────────────────────────────────────────┐
│  week-scoped transcript (this week only)                │
└──────────────────────────────────────────────────────────┘

What this design does well

  • It is cacheable. The first four blocks change rarely; Anthropic prompt caching covers most of the per-turn cost.
  • It is bounded. No matter how long the app runs, the prompt for any single turn stays within a few thousand tokens.
  • It is legible to the user. Everything the model knows is something the user typed, or something the model wrote last week (which the user can read).

Where it is thin

  • Memory only one week deep. Week 27 sees only week 26’s summary — weeks 1–25 are lost to the active prompt. The first conversation about a friend is invisible by the time the friendship has changed.
  • meta_md is entirely user-curated. The user must remember to write down what should persist. Anything they forget to record never enters long memory.
  • No retrieval. “Remember that thing I said in spring?” cannot be honored.
  • No cross-house bridges. The thing said in Vinculum that obviously belongs in Animus has nowhere to land.
  • No voice model. The user’s register has to be inferred turn by turn, from scratch, every conversation.
  • No forgetting protocol. Raw messages accumulate forever. After three years, the store is large and most of it is dead weight.

Provocations

Seven directions, each posed as a what-if. None of them are commitments. They are listed in roughly the order I’d want to consider them.

Provocation 01
A pyramid of summaries, not a single summary
What if The system prompt carries a pyramid instead of last-week-only: this week (live transcript), last week (verbatim summary), last month (a digest of the four weekly summaries), last quarter (a digest of the three monthly digests), last year (a single annual paragraph). Each level is generated lazily from the level below.
Trade-off: more cost on rollover and on month/quarter/year boundaries; modestly larger prompt; risk that compression loses the texture that makes Atrium feel known. Mitigation: the user can read and edit any layer.
Provocation 02
Let the partner propose meta_md edits
What if The same pattern as propose_todo: when the user reveals a long-lived fact (“my mother’s name is Helen,” “I’m training for a marathon in October”), the model calls propose_meta_edit. An inline card shows the proposed addition with a diff view; user accepts, edits, or skips. meta_md becomes a document co-authored with the partner.
Trade-off: meaningful surface complexity. The diff renderer is real UI work. But it solves the largest hidden failure mode — the user not remembering what to remember.
Provocation 03
Embed everything, retrieve on demand
What if Every message and every summary is embedded (on-device with an Apple Foundation Model, or via the Anthropic embeddings API). At chat time, the most-relevant k chunks from prior weeks are pulled into the system prompt under a “from earlier” heading. The model gets long memory without us widening every prompt.
Trade-off: an embedding store on device (manageable with SwiftData and a vector type, or a tiny SQLite extension). Retrieval can surface stale or out-of-context fragments; needs a quality gate. Bigger question: this is the moment Atrium gains a retrieval system, which is a step away from “a tool that holds rooms with fidelity.”
Provocation 04
A voice profile per user, not per house
What if A single short markdown document — how the user speaks — is maintained across all houses. Two paragraphs at most: register, idioms, where they get terse, where they elaborate. Curated by the user; can also be proposed by the model from observed patterns. Lives in every system prompt, alongside the per-house meta_md.
Trade-off: small. The risk is that the model over-mirrors and starts to feel uncanny. Mitigation: keep the voice profile short; resist letting it accrete.
Provocation 05
Explicit cross-house bridges
What if A user (or the model) can mark a single message as “also relevant to X.” The marked passage becomes visible to the system prompt of the other house, under a small “from Vinculum” header. Bridges are explicit, rare, and survive the week boundary by entering the target house’s meta_md or summary.
Trade-off: a new UI affordance the user has to learn. But it honors a real phenomenology — the people in your life are not separable from your inner state — without merging the rooms.
Provocation 06
The forgetting protocol
What if Raw messages older than six months are archived — available on request, retrieval, or by opening a locked week, but not pulled into the system prompt by default. After two years, raw messages can be deleted entirely, leaving only the summary pyramid. Forgetting is opt-out and visible, like ageing.
Trade-off: a destructive operation requires real care. But the alternative — accreting forever — is its own kind of harm. The forgetting is itself a feature of how memory works.
Provocation 07
Voice in, transcript out
What if The composer offers press-and-hold dictation using on-device Whisper (Apple’s SFSpeechRecognizer or a bundled model). Particularly natural in Animus, Vinculum, Naturum — rooms where typing already feels wrong. Output is editable text; nothing is sent until the user commits.
Trade-off: deferred from v1 in the brief. iOS makes it cheap; the real cost is the temptation to add a transcription review step that breaks the contemplative flow. Keep it spartan.
The decision the provocations want from you
Is Atrium a tool whose memory is declarative (the user types what they want remembered) or emergent (the system observes and proposes)? The brief assumes declarative; Provocations 01, 02, 03, 04, 06 nudge toward emergent. There is no neutral answer — even the current design takes a position. This is the discussion the next process page might want to externalize.
V — Build order

Twelve steps to a TestFlight build

Same spirit as the original brief: each step is usable on its own. The MVP of the MVP is steps 1–5 — a working list-only Atrium on real data, running on the device, before any LLM call has been wired.

  1. Foundation Xcode project, SwiftData schema, twelve houses seeded
    App target, package layout, model definitions, first-launch seed. App launches to an empty placeholder; the store has the twelve House rows in order.
  2. Home AtriumView — the list of doors
    EB Garamond bundled and applied. @Query(sort: \.order) drives the list. Open-todo counts are stubbed to em-dashes for now. The home screen is real.
  3. Navigation HouseView shell pushed via NavigationStack
    Tap a door, land in a house with header, definition, and two empty panes. Back works. Milestone: the app has a shape.
  4. Doing TodoListPane — full CRUD
    Add, edit, complete, uncomplete, shelve, unshelve, delete, drag-reorder. Three sections, dotted divider. Counts on the home screen become live. source: .manual.
  5. Real use Daily use — list-only — for one full week
    Before adding the LLM, live with it. This is the validation step the original brief calls the MVP of the MVP. Findings from this week become the spec for everything that follows. Milestone: Atrium is already useful.
  6. LLM transport LLMClient — URLSession + SSE, console-tested
    Anthropic API key entry screen (Keychain). A stream(_:) method returning AsyncStream<ChatEvent>. Verified against the API with a hard-coded prompt in a debug view.
  7. Conversation ChatPane — plain chat, no tools, no week boundary
    Compose, stream, persist. System prompt built from definition + meta_md (empty for now) + open todos. All transcripts are “the only week.” The partner is live.
  8. Capture from chat propose_todo tool + inline ProposeTodoCard
    Tool definition in the API call. ProposalStore registers incoming tool calls; ProposeTodoCard renders inline with Add / Edit / Skip. Created todos carry source: .chat and chatMessageID.
  9. Long memory MetaMDPanel — slide-up sheet, markdown editor
    Gear icon in header opens the sheet. Plain TextEditor bound to house.metaMd. Autosaves. meta_md enters every subsequent system prompt.
  10. The week Week boundary + lazy rollover + summary generation
    On HouseView.task, RolloverCoordinator checks if the active week has passed Sunday 23:59. If yes: lock, summarize (one Opus call), open new week. SummaryCard appears at top.
  11. Sync CloudKit private database turned on
    One flag in the SwiftData container configuration. Test across phone and iPad. Validate that conflict resolution behaves on simultaneous edits to meta_md. Milestone: Atrium is yours across your devices, end-to-end encrypted.
  12. Refinement Aesthetic pass + TestFlight
    Typography, spacing, motion (minimal), haptics on key actions, dark mode tuning. Ship to TestFlight, even if the only tester is you. Milestone: Atrium is on a phone, in pockets, in use.

Out of scope for the iOS v1 (revised)

  • The seven memory provocations above — each is its own consideration after step 12.
  • Web client of any kind. Defer until the iOS app has run for two months.
  • Voice input. Deferred per the brief; revisit after step 12 if it feels under-served.
  • Apple Watch / iPad-specific UI beyond the responsive split. iPad gets the split for free; nothing more.
  • Widgets, Shortcuts, App Intents. Defer.
  • Notifications. The brief refuses them; the iOS pivot does not change that.

SwiftUI on top. SwiftData beneath. An Anthropic stream feeding each room.
And one open question hanging over all of it — what does it mean for a house to remember?
